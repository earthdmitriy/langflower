--- Q10 [C] ---
In Langflower, these represent different levels of complexity in how the system handles code generation:

### The Difference
*   **`basic-coder` (Simple Coder):** A linear workflow. It takes a prompt, generates a block of code, and outputs it. It is best for **one-off snippets** or isolated functions.
*   **`coding-agent` (Advanced Coder):** An iterative/recursive workflow. It doesn't just "write" once; it typically follows a loop: **Plan $\rightarrow$ Write $\rightarrow$ Review $\rightarrow$ Refine**. It can handle multi-file changes and self-correct errors.

### Can `basic-coder` be the full value?
**It depends on your goal:**
*   **Yes**, if you need quick, modular pieces of code (e.g., "Write a Python function to sort a list").
*   **No**, if you need to build a complex feature from scratch. For large tasks, `basic-coder` can lose context or fail to catch logic errors that an agent would catch during its "Review" and "Refine" steps.

**Recommendation:** Start with `basic-coder` for prototyping small components, then switch to the **advanced-coder** sample workflow in the catalog when you need the system to handle complex logic autonomously.

--- Q11 [C] ---
The multi-loop coding pipeline follows these stages:

1.  **Clarify**: The model refines the initial prompt into a clear set of requirements.
2.  **Red Team**: Identifies potential edge cases, bugs, or "gotchas" before coding begins.
3.  **Coder**: Generates the actual code based on clarified requirements and red team feedback.
4.  **QA**: Runs tests (unit/integration) to verify the code's correctness.
5.  **Review**: A human-in-the-loop (HITL) or model step evaluates the logic and style.
6.  **Result HITL**: Final human approval or adjustment before finalizing the output.

### Who decides the order?
The **graph** decides the order. 

In Langflower, these stages are structured as a directed graph where each node's output feeds into the next. While the models *inside* the nodes perform the logic, the sequence and flow (the "looping" nature) are defined by the workflow structure itself.

--- Q13 [C] ---
It is **Proven but Iterative**. 

While we have moved past simple "autocomplete," a truly autonomous agent that handles a massive, complex project from a single prompt without human intervention is still evolving. Here is the breakdown:

### 1. What is Proven (The Agentic Shift)
We can now reliably implement agents that handle:
*   **Planning:** Breaking a high-level goal into sub-tasks.
*   **Execution:** Writing code, running tests, and fixing errors based on feedback.
*   **Context Awareness:** Using RAG or "Long Context" to understand the entire codebase (e.g., Cursor, Devin).

### 2. Why it is still "Partial"
Full autonomy is difficult because:
*   **Edge Cases:** LLMs can still struggle with complex architectural decisions or very specific UI nuances without human guidance.
*   **State Management:** Keeping track of how a change in `File A` affects `File Z` across a large project requires sophisticated "reasoning" loops.

### How to see this in Langflower:
Instead of building a coding agent from scratch, use the **simple-coder** or **advanced-coder** sample workflows in the catalog. They demonstrate how to structure an LLM's "thought process" into a repeatable workflow:
1.  **Plan** (LLM generates steps)
2.  **Code** (LLM writes snippets)
3.  **Verify** (LLM checks/runs code)

**Action:** If you want to build your own, start by exploring the `nodes/my-nodes/` folder to see how individual coding actions are modularized.

--- Q17 [E] ---
In Langflower:

**Soft Pause vs. Hard Stop**
*   **Soft Pause:** Suspends execution at a specific node while preserving all previous states. The workflow "waits" there (e.g., for user input or a manual trigger) and can resume exactly where it left off.
*   **Hard Stop:** Terminates the workflow path entirely. It marks the end of a branch or the entire flow.

**Does Stop create a checkpoint?**
*   **Yes.** A **Stop** node acts as a terminal point that saves the current state. When you run the workflow again, it can resume from that specific "checkpoint" rather than starting from the very beginning (unless you choose to restart).

--- Q20 [E] ---
In Langflower, you can continue from a checkpoint in two ways:

### 1. Implicit Checkpoints (Every Node)
By default, the workflow engine tracks the state of **every node** as it executes. You can technically "continue" from any node that has already finished its execution without needing to define anything explicitly.

### 2. Explicit Boundaries (`common-checkpoint` / `createCheckpoint`)
While not strictly required for the engine to function, explicit boundaries are used to create **named milestones**.

*   **Use these when:** You want to jump back to a specific logical "save point" (e.g., after a complex loop or before a branching path) rather than just the very last node executed.
*   **How it works:** When you define a `common-checkpoint`, it acts as a named anchor. You can tell the workflow to resume from that specific name, making it easier to manage long workflows where you don't want to restart from the absolute beginning.

**Summary:** 
*   **Required?** No, the engine tracks every node automatically.
*   **Recommended?** Yes, use `common-checkpoint` for major milestones to make resuming more intuitive.

--- Q21 [E] ---
No, they represent different behaviors in Langflower:

*   **Pause**: A temporary "hold." The workflow stops at a specific node, preserving all current data and state so you can resume exactly where you left off.
*   **Stop**: A final termination. The workflow ends at that point (unless it's a branch with multiple exits).
*   **Browser Disconnect**: A UI event. If you close the tab or lose internet, the execution usually continues in the background; you just lose the live visual feedback until you reconnect.
*   **Checkpoint Continue**: Resuming from a saved "snapshot." Unlike Pause (which is often linear), Checkpoints allow you to jump back to specific milestones in a workflow and start again from there.

**Summary Table:**
| Action | State Preserved? | Can Resume? | Best for... |
| :--- | :--- | :--- | :--- |
| **Pause** | Yes | Yes (Next step) | Waiting for human input or manual inspection. |
| **Stop** | No | No | Finishing a workflow or branching off. |
| **Disconnect** | Yes | Yes (Visuals only) | Moving between tabs/devices. |
| **Checkpoint** | Yes | Yes (Jump to point) | Debugging specific sections or long-running tasks. |

--- Q24 [F] ---
Agents get MCP tools via **`McpHandle`** objects, which are derived from your raw configuration.

### 1. Raw Config vs. McpHandle
- **Raw Config:** You define your servers in `.langflower/langflower.jsonc`. This is the "source of truth" where you specify the type (e.g., `stdio`, `sse`) and the command/args.
- **McpHandle:** When the workflow runs, Langflower parses that config into an `McpHandle`. The agent doesn't see the raw JSON; it uses the handle to query available tools, resources, and prompts dynamically.

### 2. Do all `mcp.servers` start immediately?
**No.** They are typically initialized when the workflow starts (or when a node requiring them is reached). 
- If you have many servers defined in your config but only use one in a specific workflow, Langflower manages the lifecycle so that they don't all need to be "active" simultaneously unless required by the current execution path.

**Actionable Tip:** To add a new tool, update your `langflower.jsonc` with the server details and then click **Update** on your custom node to refresh the handles.
